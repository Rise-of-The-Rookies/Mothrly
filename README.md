# Mothrly

Mothrly is an AI "mother" companion for your phone — a warm, slightly nagging presence that remembers the things you keep forgetting and gently supervises you through them. Instead of a silent checklist, you get a character who nudges you to take your meds, eat something that isn't instant noodles, go to bed, and check in when you've been quiet too long. You pick the persona whose voice works on you (the encouraging one, the stern one, the guilt-trip specialist), and Mothrly handles the reminders, the follow-ups, and the "did you actually do it?" part. It's supervision that feels like care rather than a productivity app.

> **Hackathon status:** this is an early build. The RevenueCat integration, navigation, and project scaffolding are wired up and working; the tab screens (Home, Personas, Supervise, Settings) and the paywall UI are still placeholders. See [Project structure](#project-structure) for what exists today.

|---|---|

| Builds & distribution | EAS Build (`eas.json` profiles: `development`, `preview`, `production`) |
| Tooling | ESLint (`eslint-config-universe`), Prettier |

## Project structure

```
mothrly/
├── app/                  # Expo Router routes — every file here is a screen
│   ├── _layout.tsx       # Root stack; configures RevenueCat at module load
│   ├── paywall.tsx       # Modal paywall (offering fetch wired, UI placeholder)
│   └── (tabs)/           # Home · Personas · Supervise · Settings
├── components/           # Reusable UI (non-route)
├── lib/
│   └── revenuecat.ts     # SDK config, offerings, purchases, entitlement hook
├── store/appStore.ts     # Zustand global store
├── app.json              # Expo config (bundle IDs, icons, plugins)
└── eas.json              # EAS Build profiles
```

Native `ios/` and `android/` directories are intentionally absent — they're generated by EAS. Configure native behaviour in `app.json`, never by hand.

## Setup

```bash
git clone <this-repo>
cd Mothrly/mothrly
npm install
cp .env.example .env     # then fill in your RevenueCat key (see below)
```

Environment variables (`.env`):

| Variable | Purpose |
|---|---|
| `EXPO_PUBLIC_REVENUECAT_API_KEY` | RevenueCat SDK key. Use a **Test Store** key for local development. |

If the key is missing, `configureRevenueCat()` logs a warning and skips SDK setup rather than crashing — the rest of the app still runs.

## Development builds with EAS

Mothrly depends on `react-native-purchases`, which contains native code and therefore **cannot run in Expo Go**. You need an EAS development build.

### Prerequisites

- An [Expo account](https://expo.dev/signup) (free)
- EAS CLI: `npm install -g eas-cli` or run via `npx eas-cli@latest`
- Log in: `npx eas-cli@latest login`
- Link the project to your Expo account (first time only): `npx eas-cli@latest init`

### Build profiles

| Profile | Purpose |
|---|---|
| `development` | Dev client build — use this for day-to-day development |
| `preview` | Internal distribution build for QA / stakeholder testing |
| `production` | App Store / Play Store release build |

### 1. Build the dev client

**iOS (Simulator)**
```bash
npx eas-cli@latest build --profile development --platform ios
```
The default development profile targets the iOS Simulator (`"simulator": true`). To build for a physical device, edit `eas.json` and set `"simulator": false` under `build.development.ios`.

**Android (APK)**
```bash
npx eas-cli@latest build --profile development --platform android
```

Both commands upload your project to EAS cloud, compile the native app, and provide a download link when done. No local Xcode or Android Studio required.

### 2. Install the build

- **iOS Simulator**: drag the downloaded `.app` onto a running Simulator, or use `xcrun simctl install booted <path-to.app>`.
- **iOS device**: open the EAS build link on your device to install via the Expo Go companion, or use TestFlight if you distribute through it.
- **Android**: download the `.apk` and sideload it onto your device/emulator.

### 3. Start the dev server

Once the dev client is installed, start the Metro bundler pointing at it:

```bash
npx expo start --dev-client
```

Open the installed app on your device/simulator — it will present a launcher screen where you can connect to the local dev server.

### Preview & production builds

```bash
# Internal distribution (QA / testers)
npx eas-cli@latest build --profile preview --platform ios
npx eas-cli@latest build --profile preview --platform android

# App Store / Play Store
npx eas-cli@latest build --profile production --platform ios
npx eas-cli@latest build --profile production --platform android
```

### Rebuilding after native changes

You only need to trigger a new EAS build when:
- Adding or updating a package with native code
- Changing `app.json` (bundle ID, permissions, plugins, etc.)
- Upgrading the Expo SDK

For JS-only changes, just restart the dev server — no rebuild needed.

## Note on RevenueCat

Mothrly's premium personas are gated behind a RevenueCat entitlement (`premium_personas`), but for this hackathon submission we run RevenueCat in **Test Store** mode.

Test Store is RevenueCat's sandbox backend: it serves real offerings and packages and returns real `CustomerInfo` and entitlement objects, but purchases are simulated entirely on RevenueCat's side. That means no App Store Connect or Google Play Console product setup, no paid developer account, and no real money — while still exercising the same SDK code paths that production would.

What this means for anyone running the project:

- The key in `.env.example` is meant to be a **Test Store key** (they're prefixed `test_`). Purchases made with it are not real transactions.
- `lib/revenuecat.ts` deliberately configures a single cross-platform key. Test Store keys aren't platform-specific; real App Store / Play Store keys are, so that call will need to branch on `Platform.OS` before shipping.
- Entitlement checks, the `CustomerInfo` listener, purchase, and restore flows are all production-shaped code. Switching to live billing is a matter of swapping keys and configuring store products — not rewriting the integration.

## Secrets

- `.env` is gitignored and is **not** part of this repository. Only `.env.example`, which contains placeholders, is tracked.
- Note that any `EXPO_PUBLIC_*` variable is inlined into the JavaScript bundle at build time and is therefore readable by anyone with the app. This is expected for RevenueCat SDK keys (they're public by design), but never put a secret — a RevenueCat *secret* API key, a backend token, an LLM provider key — behind an `EXPO_PUBLIC_` prefix. Those belong on a server.
